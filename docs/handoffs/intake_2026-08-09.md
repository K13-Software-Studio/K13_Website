# Intake assessment — K13 Website

**Project:** `/Users/k13/Desktop/PROJECTS/K13_Website` — K13 Software Studio's own shopfront/portfolio site.
**Assessed by:** Selma (Solutions Architect, intake) — assess-only pass, no files modified outside `docs/`.
**Date:** 2026-08-09

## What this project actually is

This is **not** a green-field project. It's a mature, actively-shipped site: 12 `beta_v*` branches, 4
`site13_jul03_v*` branches, 7 merged PRs, most recent commit 2026-07-03. `index.html` (831 lines, single
file, zero build step) is K13's own marketing/portfolio shopfront — hero, "three rules" approach section,
a "Selected work" index of 10 live production projects (Tiger Hospitality, La Vida, Miramar, Station8,
Global Fork, Egg&Out, TrustMeBro, baa atelier, BarFix, CENGO), a "three lanes" capabilities section
(products end-to-end / brand sites / hard specific stuff), an about section, and a multi-step contact
form that opens the visitor's mail client (no backend). `README.md` (2.6KB) already documents the brand
thoroughly: the K-from-1-and-3 mark concept, a full hex palette, the two-typeface system (Space
Grotesk + Fraunces Italic), contact routing, and hosting (Vercel, `main` → production, branch pushes →
stakeholder previews). This is a settled brand, not one still forming.

## The three known gaps — verified, not assumed

1. **No `CLAUDE.md` in project root.** Confirmed genuinely absent (`ls CLAUDE.md` → no such file). There
   is a `.claude/` directory, but it only holds `settings.json`/`settings.local.json` (tool permissions
   for gstack's headless-browser skill) — no project-instructions file, and `.claude/` is gitignored so
   none of it is version-controlled or shared with a fresh agent by default.
2. **No `PROJECT_BRIEF.md` or `SCOPE.md`.** Confirmed absent — there was no `docs/` directory at all
   before this pass created `docs/handoffs/`. That said, the project isn't undocumented: `README.md`
   already covers what/for-whom/brand/hosting at a level that substitutes for most of a brief. What's
   missing is the house-standard artifact a fresh agent would look for by convention, plus any written
   "in scope / out of scope" boundary — there is none, so an agent can't currently tell at a glance
   whether e.g. adding new case studies, restructuring nav, or touching `pricing/` is in bounds.
3. **Dev port — partially a non-issue.** Checked `starter-kit/CONVENTIONS.md` in the War Room repo:
   **port 9130 is already claimed** for K13 Website (shortcode `site`, static) in the 9130–9199 registry
   — this isn't actually missing at the org level. What's missing is (a) that claim isn't recorded
   anywhere *in this repo* (no `CLAUDE.md` to hold it), and (b) there's nothing to pin it to — this
   project has no local dev server at all. Per `README.md`, the workflow is "open `index.html` directly
   or upload to a web root"; `scripts/` holds only git-workflow helpers (`hm.sh`, `new-branch.sh`,
   `ship.sh`, `setup-identity.sh`), no serve script. So the port row exists and is correct, it's just
   unwired — low-severity given the site needs no build/serve step to work on locally.

## Is the scope clear enough for another agent to pick up work?

Mostly yes for *understanding the site*, no for *knowing the boundaries*. `README.md` + `index.html`
let a fresh agent infer what the site is and how it's built accurately. What's missing is anything that
states current priorities, what's explicitly out of scope, or open questions — there's no single place
a new agent lands to get oriented the way `CLAUDE.md` normally provides.

## Recommendation

Treat this as a **light P0 catch-up**, not a from-scratch scaffold: the project already works, ships,
and is reasonably self-documented. What it needs is the house-standard connective tissue — a
`CLAUDE.md` that points at the existing `README.md` instead of duplicating it, a short
`PROJECT_BRIEF.md`/`SCOPE.md` that states what's in/out of bounds (e.g., is `pricing/` in scope for this
repo at all?), and writing the already-claimed port 9130 into that `CLAUDE.md` for the record. That's a
build task, not an assess task, so it's flagged here rather than done in this pass.
